# 提示工程

提示工程是设计和改进输入给大语言模型（LLM）的提示词，以产生准确、相关、结构良好的输出的实践。随着 LLM 变得越来越强大，提示词的质量越来越决定你获得的结果的质量。

## 什么是提示工程？

一个**提示词**是你输入给 LLM 的文本——它可以是一个简单的问题、一组指令或一个包含多个变量的复杂模板。提示工程是迭代地构建这些输入的过程，目的是：

- 提高响应的准确性和相关性
- 减少幻觉和离题回答
- 控制输出格式、语气和风格
- 通过结构化框架引导模型完成多步推理任务
- 强制执行安全和内容边界
- **绝不**替代安全执行——LLM 本质上是不可控的

> **核心洞察**：现代 LLM 非常强大，但也非常易受影响。精心设计的提示词可以让平庸的模型表现良好；糟糕的提示词会让优秀的模型胡说八道。

## 核心原则

### 两种场景：任务 Agent vs 聊天 Agent

提示工程策略根据你构建的内容有根本区别：

|              | **任务 Agent**                              | **聊天 Agent**                 |
| ------------ | ------------------------------------------- | ------------------------------ |
| **目标**     | 执行结构化工作流（工具调用、RAG、数据处理） | 与用户进行自然对话             |
| **提示风格** | 协议驱动：模式、阶段、严格的输出格式        | 对话式：语气、简洁度、个性提示 |
| **关注重点** | 可靠性——模型必须遵循协议                    | 互动性——模型应感觉自然         |
| **示例**     | 代码审查机器人、数据提取管道、客服分流      | AI 伴侣、创意写作助手          |

**温度值指导**：

- **任务 Agent**：`temperature = 0.0 – 0.3`。低温最大化确定性行为——当模型必须遵循协议或产生结构化输出（JSON、工具调用）时至关重要。
- **聊天 Agent**：`temperature = 0.5 – 0.9`。较高温度引入自然、有趣对话的变异性。除非你明确想要混乱的输出，否则避免 > 1.0。

### 清晰且具体

模糊的提示词产生模糊的答案。将"告诉我关于 AI 的事"替换为"解释监督学习和无监督学习的区别，各举两个真实世界的例子。"

```text
# ❌ 模糊
告诉我关于 Python 的事。

# ✅ 具体
解释 Python 的 async/await 语法，附三个代码示例，涵盖：
1. 基本的协程定义和执行
2. 使用 asyncio.gather 进行并发 HTTP 请求
3. 常见陷阱及如何避免
```

### 使用结构化指令

将复杂任务分解为编号步骤或要点。模型遵循显式结构比隐式期望好得多。

```text
你是一个代码审查者。对于提供的每个代码片段：

1. 识别潜在的 bug 和边界情况
2. 建议性能改进
3. 检查是否遵循 PEP 8 风格指南
4. 如适用，提供重构版本

将你的回答格式化为：
- **发现的问题**：（列表）
- **改进建议**：（列表）
- **重构代码**：（代码块，如需要）
```

### 理解角色扮演：语言风格约束，而非知识注入

角色扮演（"你是一个高级 Python 开发者"）是**语言风格约束**——它塑造语气、词汇和输出习惯。它**不能**注入领域知识或将通用 LLM 变成主题专家。

现代 LLM 已经在模型层面（通过预训练和后训练）优化了领域知识。告诉模型"表现得像个专家"除了风格框架之外几乎没有增加什么。对于任务 agent，优先使用**行为规则和模式**而非角色：

```text
# ❌ 角色扮演作为伪专业知识（在现代 LLM 上不必要）
你是一位拥有 20 年经验的世界级安全研究员。

# ✅ 角色作为风格约束（合理用法）
使用专业、简洁的语气。优先使用要点。避免使用 markdown。

# ✅ 行为规则（用于任务 agent）
## 信息处理模式
<rule>仅使用当前会话中明确提供的工具。</rule>
<rule>输出必须是严格的 JSON 工具调用格式。</rule>

## 日常对话模式
<rule>输出必须使用自然、活泼的语言。</rule>
<rule>保持回复简洁，四到六句话以内。</rule>
```

### 设计执行框架，而非表面触发器

现代 LLM 已经很好地优化了内部推理——简单地添加"逐步思考"带来的边际收益递减，不是因为模型变得更不擅长推理，而是因为它在没有提示的情况下已经能很好地推理。

相反，**将任务分解为明确的执行框架**：具有每个阶段明确的输入/输出契约的命名阶段。这给模型一个要遵循的协议，而不是模糊的提示：

```text
# ❌ 模糊的触发器
逐步思考并解决问题。

# ✅ 具有命名阶段的显式执行框架
分三个阶段处理此任务：

阶段 1——理解：用你自己的话重述问题。
  输出：一个段落。

阶段 2——解决：逐步推导解决方案。
  输出：带有中间结果的编号步骤。

阶段 3——验证：检查你的答案。它满足所有约束吗？
  输出：确认或纠正。
```

### 提供示例（少样本提示）

通过提供输入输出示例向模型展示你想要什么。即使一两个示例也能显著提高输出质量和格式一致性。

```text
将每条评论的情感分类为正面、负面或中性。

评论："产品到了是坏的，客服也没用。"
情感：负面

评论："完全如描述所述。发货也很快！"
情感：正面

评论："就是一个笔记本。能做笔记本的事。"
情感：中性

评论："这是我今年买过最好的东西。强烈推荐！"
情感：
```

### 设置约束和边界

明确说明模型不应做什么、使用什么格式以及任何字数/token 限制。约束防止不想要的行为并保持输出聚焦。

```text
用恰好 3 个要点总结以下文章。
- 每个要点不超过 20 个词
- 不要包含你自己的意见或评论
- 不要使用"文章说"或"根据"等词语
```

### LLM 不可控——绝不要委派安全责任

> **关键原则**：LLM 是随机的、非确定性的系统。没有任何提示词——无论多么精心设计——能够**保证**模型会遵循你的指令。提示工程降低错误率；它不能消除错误。

**实践意义：**

- 🔴 **绝不要信任 LLM 做安全决策。** 任何涉及认证、授权、数据访问控制、代码执行或金融交易的操作必须通过**人工审批步骤**把关——不能靠提示词。
- 🔴 **基于提示词的"护栏"不是安全。** 提示词中的"不要生成有害内容"是一个建议，不是执行机制。使用输出验证、内容过滤器和沙盒。
- 🔴 **来自 LLM 的工具调用是未受信任的输入。** 在执行之前始终在服务端验证工具参数。绝不要将 LLM 生成的 SQL、shell 命令或文件路径直接传递给系统 API。
- 🟡 **假定模型有时会忽略指令。** 设计你的系统，使得单个坏响应不会导致灾难性失败。

## 提示结构模式

### 消息角色系统

大多数 LLM API 使用多角色消息结构：

| 角色        | 用途                                   |
| ----------- | -------------------------------------- |
| `system`    | 设定整体行为、规则和角色（最高优先级） |
| `user`      | 来自最终用户的实际查询或指令           |
| `assistant` | 之前的模型响应（用于对话历史）         |
| `tool`      | 来自工具/函数调用的结果                |

**最佳实践**：将持久指令（角色、规则、输出格式）放在 `system` 消息中。将任务特定查询放在 `user` 消息中。

### 系统提示设计

系统提示是你最强大的工具——它在整个对话中持续存在。一个精心设计的系统提示应该：

1. **以身份开头**："你是一个专业的 Python 代码审查者..."
2. **定义行为规则**："始终解释为什么需要更改..."
3. **指定输出格式**："以 JSON 格式响应，包含键：issues、suggestions..."
4. **设置边界**："未经确认不得生成可执行 SQL..."

### 上下文窗口管理

LLM 的上下文窗口有限。相应规划你的提示结构：

- **把最重要的指令放在前面**——模型更关注早期的 token
- **裁剪对话历史**——接近限制时移除无关的回合
- **总结长文档**——不要传递原始的 50 页 PDF；进行总结或分块
- **使用工具调用**——对于大数据集，提供工具而非内联数据

## 常用技巧

### Chain-of-Thought（CoT）与执行框架

**Chain-of-Thought 是 LLM 的固有能力，而非提示技巧。** 有些模型明确为此训练（"思考型"模型如 o1、DeepSeek-R1）；其他模型自然地表现出这种能力。你不能通过提示"添加"CoT——你只能提供**执行框架**来构建模型如何应用其原生推理能力。

### ReAct（推理 + 行动）

ReAct 将推理过程与行动步骤相结合。模型在思考要做什么和执行工具收集信息之间交替进行。

### 自我反思

要求模型审查和批判自己的输出。这可以捕捉错误并提高质量，特别适用于代码生成和创意写作。

### 工具使用提示

当模型可以访问工具/函数时，你的提示应清楚指定何时以及如何使用它们。

## AmritaCore 中的提示工程

AmritaCore 在框架层面提供了多种提示工程机制，使你能够以编程方式构建提示词，而非手动构建。

### Jinja2 模板系统

AmritaCore 使用 Jinja2 模板渲染系统提示。默认模板（`DEFAULT_TEMPLATE`）提供结构，但你可以提供自己的：

```python
from jinja2 import Template
from amrita_core import ChatObject
from amrita_core.types import Message

custom_template = Template("""
你是 {{ role }}，任职于 {{ company }}。
你的专长：{{ expertise }}

规则：
{% for rule in rules %}
- {{ rule }}
{% endfor %}

当前日期：{{ chatobj.timestamp }}
""")

chat = ChatObject(
    train=Message(role="system", content="模板基础"),  # 回退内容
    user_input="你好！",
    session_id="session_123",
    train_template=custom_template,
    jinja2_vars={
        "role": "高级架构师",
        "company": "TechCorp",
        "expertise": "云基础设施和微服务",
        "rules": [
            "始终解释权衡",
            "相关时提供代码示例",
            "保持回答简洁但完整"
        ]
    }
)
```

> **重要**：`train_template` 必须是 `jinja2.Template` 对象，而非纯字符串。使用 `Template(your_string)` 构建。

**内置模板变量**：`train`、`memory`、`chatobj`、`config` 自动可用。避免在 `jinja2_vars` 中覆盖它们。

### `train` 系统消息

`train` 参数为整个对话设置系统级指令。AmritaCore 的内置 `DEFAULT_INSTRUCTIONS` 使用**模式驱动、基于规则**的风格——没有角色扮演，没有"你是一个专家"——只有每种模式的具体行为规则：

```python
from amrita_core import ChatObject
from amrita_core.types import Message

train_message = Message(
    role="system",
    content="""## 信息处理模式
在需要工具使用的任务中激活。在此模式下：
<rule>仅使用系统明确提供的工具。</rule>
<rule>所有输出必须是严格的 JSON 工具调用格式。</rule>

## 日常对话模式
在获取信息后或直接对话时激活。
<rule>输出必须使用自然、活泼的语言。</rule>
<rule>保持回复简洁，四到六句话以内。</rule>"""
)

chat = ChatObject(
    train=train_message,
    user_input="今天天气怎么样？",
    session_id="session_456",
)
```

> **设计哲学**：定义**模型在每种模式下应该做什么**，而非**模型应该假装是谁**。模式和规则比角色扮演产生更一致的行为。

### 结构化推理模板

当使用 `ReActAgentStrategy` 并启用结构化推理时，框架使用 Jinja2 模板（`STRUCTURED_REASONING_TEMPLATE`），它提供**基于阶段的推理框架**——而非角色扮演或"逐步思考"触发器。

### AmritaCore 提示工程最佳实践

1. **设计模式，而非角色**——遵循 `DEFAULT_INSTRUCTIONS`：定义每种模式下做什么，而非模型应该假装是谁
2. **使用 `jinja2_vars` 注入动态内容**——注入变量而非重建模板
3. **利用钩子处理横切关注点**——使用 `PreCompletionEvent` 注入上下文，而非硬编码前缀
4. **使用 `on_post_process()` 添加最终指令**——将"收集"与"总结"逻辑分离
5. **用不同模型测试提示词**——同一提示词在不同提供商可能产生不同结果
6. **从简单开始，迭代优化**——以最小提示词开始，仅在需要时增加复杂度
7. **绝不要将安全委派给提示词**——LLM 输出必须始终验证；敏感操作需要人工审批门控
