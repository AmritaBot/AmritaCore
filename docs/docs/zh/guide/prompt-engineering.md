# 提示工程

提示工程是设计和优化输入给大语言模型（LLM）的提示词（Prompt）以产生准确、相关且结构良好输出的实践。随着 LLM 能力的不断增强，提示词的质量越来越决定输出结果的质量。

## 1. 什么是提示工程？

**提示词**是输入给 LLM 的文本——可以是一个简单的问题、一组指令或一个包含多个变量的复杂模板。提示工程是不断迭代优化这些输入的过程，目的是：

- 提高响应的准确性和相关性
- 减少幻觉和偏离主题的回答
- 控制输出格式、语气和风格
- 引导模型通过结构化框架完成多步推理任务
- 强制执行安全和内容边界
- **绝不**替代安全措施 —— LLM 本质上不可控

> **核心见解**：现代 LLM 能力极强，但也极易受影响。精心设计的提示词能改善输出质量；但任何提示词都无法**保证**模型遵守指令 —— 提示工程降低错误率，不消除错误。

## 2. 核心原则

### 2.0 两种场景：任务型 Agent 与 聊天型 Agent

提示工程策略因构建目标不同而有本质差异：

|                | **任务型 Agent**                            | **聊天型 Agent**               |
| -------------- | ------------------------------------------- | ------------------------------ |
| **目标**       | 执行结构化工作流（工具调用、RAG、数据处理） | 与用户进行自然对话             |
| **提示风格**   | 协议驱动：模式、阶段、严格的输出格式        | 对话式：语气、简洁性、个性提示 |
| **核心关注点** | 可靠性——模型必须遵循协议                    | 参与感——模型应该自然流畅       |
| **示例**       | 代码审查机器人、数据提取流水线、客服分诊    | AI 伴侣、创意写作助手          |

**温度调优参考**：

- **任务型 Agent**：`temperature = 0.4 – 0.7`。低温最大化确定性行为——当模型必须遵循协议或产生结构化输出（JSON、工具调用）时至关重要。
- **聊天型 Agent**：`temperature = 0.8 – 1.2`。较高温度引入变化，使对话自然生动。除非刻意追求混乱输出，避免 >1.3。

以下原则（§2.1–§2.7）适用于两种场景，但侧重点不同：**任务型 Agent** 优先结构约束（§2.2、§2.6）和执行框架（§2.4）；**聊天型 Agent** 优先清晰度（§2.1）、示例（§2.5）和语气控制（§2.3）。

### 2.1 清晰明确

模糊的提示词产生模糊的回答。将"给我讲讲 AI"替换为"解释监督学习和无监督学习的区别，每种给出两个真实世界的例子。"

```text
# ❌ 模糊
给我讲讲 Python。

# ✅ 明确
解释 Python 的 async/await 语法，包含三个代码示例，涵盖：
1. 基本的协程定义和执行
2. 使用 asyncio.gather 进行并发 HTTP 请求
3. 常见陷阱及如何避免
```

### 2.2 使用结构化指令

将复杂任务分解为编号步骤或要点。模型对显式结构的遵循远好于对隐含期望的理解。

```text
你是一位代码审查者。对于提供的每个代码片段：

1. 识别潜在的 bug 和边界情况
2. 提出性能改进建议
3. 检查是否符合 PEP 8 风格指南
4. 如适用，提供重构后的代码

按以下格式回复：
- **发现的问题**：（列表）
- **改进建议**：（列表）
- **重构代码**：（代码块，如需要）
```

### 2.3 理解角色扮演：语言风格约束，而非知识注入

角色扮演（"你是一位资深 Python 开发者"）是一种**语言风格约束**——它塑造语气、词汇和输出风格。它**不能**注入领域知识或将一个通用 LLM 变成真正的领域专家。

现代 LLM 在模型层面已对专业知识做了充分优化（通过预训练和后训练）。告诉模型"表现得像个专家"除了风格框架之外几乎没有额外收益。对于任务型 Agent，应优先使用**行为规则和模式**而非人设：

```text
# ❌ 人设作为虚假专业身份（对现代 LLM 无必要）
你是一位拥有 20 年经验的世界级安全研究员。

# ✅ 人设作为风格约束（合理使用）
使用专业、简洁的语气。优先使用项目符号。避免使用 markdown。

# ✅ 行为规则（用于任务型 Agent）
## 信息处理模式
<rule>仅使用系统在本次会话中明确提供的工具。</rule>
<rule>输出必须为严格的 JSON 工具调用格式。</rule>

## 日常对话模式
<rule>输出必须使用自然、生动的语言。</rule>
<rule>保持回复简洁，控制在四至六句话以内。</rule>
```

关键区分：

- **风格人设**（语气、长度、格式）——合理、可测试
- **专业身份人设**（"你是 X 领域的专家"）——无必要；模型如果在训练数据中有 X 的知识，它本来就知道
- **行为规则**（模式、协议、约束）——对任务型 Agent 来说比以上两种都更可靠

### 2.4 设计执行框架，而非表面触发词

现代 LLM 已对内部推理做了充分优化——简单加一句"逐步思考"的边际收益越来越低，不是因为模型推理能力退步，而是因为它已经足够好，无需这个提示。

应当**将任务分解为显式的执行框架**：命名的阶段，每个阶段有明确的输入/输出约定。这为模型提供了可遵循的协议，而非模糊的提示：

```text
# ❌ 模糊的触发词
逐步思考并解决问题。

# ✅ 带有命名阶段的显式执行框架
按三个阶段处理此任务：

阶段一 — 理解：用自己的话重述问题。
  输出：一个段落。

阶段二 — 求解：逐步推导解答，展示每个步骤。
  输出：编号步骤及中间结果。

阶段三 — 验证：检查你的答案。是否满足所有约束？
  输出：确认或修正。
```

**为什么有效**：思维链是 LLM 自身的能力，不是通过提示词"添加"的。你能控制的是**执行协议**——命名阶段的顺序、各阶段的预期输出以及模型必须遵循的格式。模型在该结构内运用其原生推理能力。你定义*遵循什么阶段*；模型决定*在每个阶段内如何思考*。

### 2.5 提供示例（少样本提示）

通过提供输入-输出示例向模型展示你期望的效果。即使一两个示例也能显著提升输出质量和格式一致性。

```text
将每条评论的情感分类为正面、负面或中性。

评论："产品到货时已经损坏，客服也没有帮助。"
情感：负面

评论："完全符合描述。物流也很快！"
情感：正面

评论："就是个笔记本电脑。能做笔记本电脑该做的事。"
情感：中性

评论："今年最值的购物体验。强烈推荐！"
情感：
```

### 2.6 设置约束和边界

明确说明模型不应该做什么、使用什么格式以及词数/Token 限制。约束可防止不期望的行为并保持输出聚焦。

```text
用恰好 3 个要点总结以下文章。
- 每个要点不超过 20 个词
- 不要包含您自己的观点或评论
- 不要使用"文章说"或"根据"等措辞
```

### 2.7 LLM 不可控 —— 绝不将安全委托给提示词

> **关键原则**：LLM 是随机的、非确定性的系统。任何提示词——无论设计得多么精心——都无法**保证**模型会遵循你的指令。提示工程降低错误率；它不能消除错误。

**实践含义：**

- 🔴 **绝不相信 LLM 做安全决策。**任何涉及认证、授权、数据访问控制、代码执行或金融交易的操作，必须由**人工审批环节**把关——而非提示词。
- 🔴 **基于提示词的"护栏"不是安全措施。**提示词中写"不要生成有害内容"只是建议，不是强制机制。应使用输出验证、内容过滤和沙箱环境。
- 🔴 **来自 LLM 的工具调用是不可信的输入。**始终在服务端验证工具参数后再执行。绝不要将 LLM 生成的 SQL、shell 命令或文件路径直接传递给系统 API。
- 🟡 **假定模型有时会忽略指令。**设计系统时确保单次错误响应不会导致灾难性故障。

> AmritaCore 提供 **cookie 安全检测**和**内容过滤钩子**，但这些是纵深防御层——不能替代敏感操作的人工审批。

## 3. 提示结构模式

### 3.1 消息角色系统

大多数 LLM API 使用多角色消息结构：

| 角色        | 用途                                   |
| ----------- | -------------------------------------- |
| `system`    | 设定整体行为、规则和人设（最高优先级） |
| `user`      | 来自终端用户的实际查询或指令           |
| `assistant` | 模型的前序响应（用于对话历史）         |
| `tool`      | 工具/函数调用的结果                    |

**最佳实践**：将永久性指令（人设、规则、输出格式）放在 `system` 消息中。将任务特定的查询放在 `user` 消息中。

### 3.2 系统提示词设计

系统提示词是你最强大的工具——它在整个对话中持续有效。精心设计的系统提示词应：

1. **以身份开头**："你是一位资深 Python 代码审查专家……"
2. **定义行为规则**："始终解释为什么需要此变更……"
3. **指定输出格式**："以 JSON 格式回复，包含键：issues、suggestions……"
4. **设定边界**："未经确认，绝不生成可执行的 SQL 语句……"

### 3.3 上下文窗口管理

LLM 的上下文窗口有限。相应规划提示词结构：

- **把最重要的指令放在前面**——模型对前面的 token 关注度更高
- **裁剪对话历史**——接近限制时移除无关的对话轮次
- **总结长文档**——不要直接传入 50 页的原始 PDF；先总结或分块
- **使用工具调用**——对于大数据集，提供工具而非内联数据

## 4. 常用技术

### 4.1 思维链（Chain-of-Thought）与执行框架

**思维链是 LLM 自身的能力，而非提示技巧。** 部分模型专门为此训练（"thinking" 模型如 o1、DeepSeek-R1）；其他模型则自然展现。你无法通过提示词"添加" CoT 到模型中——你只能提供**执行框架**，结构化地引导模型运用其原生推理能力。

有效的做法是定义模型必须经历的显式阶段，让其内置的 CoT 填充每个阶段：

```text
使用四个推理阶段分析此问题：

[analyze]  用自己的话重述问题。识别未知量。
[plan]     列出解决步骤，如适用附上公式。
[execute]  逐步执行，展示计算过程。
[verify]   将答案对照原始问题进行检查。

问题：商店有 120 个苹果。上午卖出 30%，下午卖出剩余的 25%。还剩多少苹果？
```

> **关键区分**：CoT 是模型的内部过程；编号阶段是你施加的**执行协议**。不要混为一谈——"逐步思考"是语言风格提示，不是 CoT 工程。

### 4.2 ReAct（推理 + 行动）

ReAct 将推理轨迹与行动步骤结合。模型在思考下一步做什么和执行工具获取信息之间交替进行。

```text
你可以使用搜索工具。对于每个问题：
1. 思考：我需要什么信息？
2. 行动：调用搜索工具
3. 观察：分析搜索结果
4. 思考：信息是否足够回答问题？
5. 如果足够，给出答案。如果不够，继续搜索。
```

### 4.3 自我反思

要求模型审查并评判自己的输出。这可以捕捉错误并提高质量，尤其适用于代码生成和创意写作。

```text
生成答案后，请审查：
1. 事实准确性——所有主张是否有依据？
2. 完整性——是否回答了问题的每个部分？
3. 清晰度——初学者能理解吗？

如有需要，提供修订后的版本。
```

### 4.4 工具使用提示

当模型可以访问工具/函数时，提示词应明确指定何时及如何使用：

```text
你可以使用以下工具：
- search_web(query: str) —— 搜索互联网
- calculate(expression: str) —— 计算数学表达式

规则：
- 对不确定的事实性问题使用 search_web
- 对于基础算术以外的数学计算使用 calculate
- 当工具能给出正确答案时，绝不要猜测
```

## 5. AmritaCore 中的提示工程

AmritaCore 在框架层面提供了多种提示工程机制，使您能以编程方式构建提示词，而非手工编写。

### 5.1 Jinja2 模板系统

AmritaCore 使用 Jinja2 模板渲染系统提示词。默认模板（`DEFAULT_TEMPLATE`）提供基础结构，但您可以提供自定义模板：

```python
from jinja2 import Template
from amrita_core import ChatObject
from amrita_core.types import Message

custom_template = Template("""
你是 {{ company }} 的 {{ role }}。
专业领域：{{ expertise }}

规则：
{% for rule in rules %}
- {{ rule }}
{% endfor %}

当前日期：{{ chatobj.timestamp }}
""")

chat = ChatObject(
    train=Message(role="system", content="模板基础"),  # 回退内容
    user_input="你好！",
    session_id="session_123",
    train_template=custom_template,
    jinja2_vars={
        "role": "资深架构师",
        "company": "TechCorp",
        "expertise": "云基础设施和微服务",
        "rules": [
            "始终解释权衡取舍",
            "相关时提供代码示例",
            "回答简洁但完整"
        ]
    }
)
```

> **重要**：`train_template` 必须是 `jinja2.Template` 对象，不能直接传裸字符串。使用 `Template(your_string)` 构造。

**内置模板变量**：`train`、`memory`、`chatobj`、`config` 自动可用。避免在 `jinja2_vars` 中覆盖它们。

### 5.2 `train` 系统消息

`train` 参数为整个对话设置系统级指令。AmritaCore 内置的 `DEFAULT_INSTRUCTIONS` 采用**模式驱动、规则为本**的风格——不使用人设、不用"你是一个专家"——只为每种模式定义具体行为规则：

```python
# AmritaCore 的方式：模式驱动，规则为本
# （简化自 consts.py 中的实际 DEFAULT_INSTRUCTIONS）
from amrita_core import ChatObject
from amrita_core.types import Message

train_message = Message(
    role="system",
    content="""## 信息处理模式
当任务需要使用工具时激活。在此模式下：
<rule>仅使用系统明确提供的工具。</rule>
<rule>所有输出必须为严格的 JSON 工具调用格式。</rule>

## 日常对话模式
获取信息后或直接聊天时激活。
<rule>输出必须使用自然、生动的语言。</rule>
<rule>保持回复简洁，控制在四至六句话以内。</rule>

## 模式选择
调用 agent_stop 工具从信息处理模式切换到日常对话模式，
然后提供最终响应。"""
)

chat = ChatObject(
    train=train_message,
    user_input="今天天气怎么样？",
    session_id="session_456",
)
```

> **设计理念**：定义**模型在每种模式下应该做什么**，而非**模型应该假装是谁**。模式和规则比人设产生更一致的行为。

### 5.3 结构化推理模板

使用启用了结构化推理的 `ReActAgentStrategy` 时，框架使用 Jinja2 模板（`builtins/consts.py` 中的 `STRUCTURED_REASONING_TEMPLATE`），提供**基于阶段的推理框架**——而非人设或"逐步思考"触发词：

模板引导模型经历以下阶段：

1. **[analyze]** — 理解用户输入，识别需求
2. **[plan]** — 制定策略，选择工具
3. **[execute]** — 执行操作，调用工具
4. **[verify]** — 对照目标验证结果

配置控制：

```python
from amrita_core.config import AmritaConfig

config = AmritaConfig()
config.builtin.react_config.reasoning_depth = 3  # 最大推理步数
config.builtin.react_config.tool_prediction = True  # 预测所需工具
```

> **CoT 与执行框架的区别**：思维链是模型自身的内部推理过程——你无法通过提示词控制它。`STRUCTURED_REASONING_TEMPLATE` 提供的是**执行协议**：命名的阶段、显式的输出格式和固定的推理分类体系。框架定义*遵循什么结构*；模型的原生 CoT 处理*在该结构内如何思考*。

### 5.4 AmritaCore 提示工程最佳实践

1. **设计模式，而非人设**——遵循 `DEFAULT_INSTRUCTIONS`：定义每种模式下该做什么，而非模型该假装是谁
2. **使用 `jinja2_vars` 处理动态内容**——注入变量而非重建模板
3. **利用钩子处理横切关注点**——使用 `PreCompletionEvent` 注入上下文，而非硬编码前缀
4. **使用 `on_post_process()` 添加最终指令**——将"收集"逻辑与"总结"逻辑分离
5. **用不同模型测试提示词**——同一提示词在不同提供商上可能产生不同结果
6. **从简单开始，逐步迭代**——从最小提示开始，仅在需要时增加复杂度
7. **绝不将安全委托给提示词**——LLM 输出必须始终验证；敏感操作需要人工审批环节
